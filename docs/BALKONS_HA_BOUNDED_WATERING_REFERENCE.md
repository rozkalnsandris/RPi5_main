The existing HA preview, Telegram STOP and legacy watering schedule are unchanged. The ESP32 candidate is merged source, not installed firmware evidence.

The native reference uses one single-mode admission script, a non-restored default-OFF owner arm latch, a default-ON incomplete-attempt latch, a reply mailbox and a disabled 11:00 local schedule. The second latch prevents an interrupted attempt from silently becoming eligible on a later day while the owner arm remains ON. No code automatically turns the arm ON. Recovery and any future arm transition require a separate reviewed procedure. The source contains literal false entry gates in both scripts and the scheduler, and additional false session/transport-proof and release conditions in the start sequence. Turning a helper or automation ON cannot release it.

## Admission and reply handling

The existing preview is a negative filter for weather, clock, date and software pump state, never a live permit. Its computed minimum temperature must be a finite numeric value strictly above 2 C, with a recognized outcome. Sensor-only preview outcomes do not establish or veto fresh sensor admission: the preview reads retained categorical entities, whereas the actual moisture gate consumes the new device scan. The date/pump/arm/pending guards remain. The current weather state, temperature and unit are captured and must remain unchanged before dispatch; this does not prove the forecast cannot change in the interim. Freeze the arm state generation (state context ID and `last_changed`) before the forecast call. Before any protocol dispatch latch pending and freeze its ON generation. Recheck both frozen generations during request, wait/capture, reservation, immediately before start, ACK and completion. An OFF-to-ON transition cannot restore an old attempt at these checked boundaries. Neither state timestamps nor context IDs are durable security tokens or atomic cross-service transactions. Do not rearm while an attempt or STOP is running. A pre-subscribed MQTT reply sensor avoids opening a one-off subscription after a fast reply.

The non-retained QoS1 request is a prefixed string `ticket45:<16 hex>`. Reject an already present matching offer prefix before dispatch. Wait at most five seconds for a matching request prefix or cancellation, capture once, then require the exact 104-character v2 payload `offer2:<16 request>:<24 ticket>:<40 revision>:<10 codes>:off`. Match the pinned firmware revision, exact lengths, lowercase hex, delimiters and OFF suffix. The old v1 format is rejected. The request and all start/ACK values remain prefixed strings to prevent native-template coercion of numeric-looking hexadecimal values. No refresh, fallback, retry, or second start. Require the captured HA mailbox update timestamp to be strictly after the request timestamp and no later than five seconds after it, with no future observation accepted. Capture payload and timestamp from one HA state object, then require the same payload AND update timestamp before reserving the day and immediately before start. A rewritten identical payload (with a new update timestamp) also blocks. This is local observation evidence, not transport proof or strict first-event capture. A malformed matching offer is not a reason to request another.

The ten codes are ordered by flowers 1, 3–10, 12. D is dry, W wet, M intermediate (blocks), U ADC-invalid/unavailable (count as assumed wet). Require <=2 U, >=2 D and W+U<8, therefore at least three D with this complete ten-channel policy. No retained moisture entity can authorize the attempt. The device scan is bounded to under two seconds and the ticket expires ten seconds from scan start; HA accepts and uses the frozen offer only within eight seconds of its request dispatch, with a five-second wait. The device still enforces the scan-start expiry. Verify date reservation/readback and unchanged weather snapshot, arm, pending, software OFF and exact frozen offer before dispatch. Any rejected or interrupted request leaves pending latched; this deliberately conservative reference requires recovery even after a no-start rejection, rather than silently permitting another attempt. The hard false conditions remain, including before ticket dispatch and before start.

A single non-retained QoS1 start uses the frozen ticket. Software ON must match it within five seconds and have a post-dispatch HA update timestamp; OFF must likewise correlate to the same ticket, have a post-dispatch update timestamp, and the switch must report OFF by the conservative HA deadline (45 seconds from dispatch, with the device deadline measured from earlier scan start). Missing, overwritten, late, or ambiguous replies fail closed; never repeat ON. On a clean correlated result, clear only pending; on uncertainty, keep pending latched, disarm, and use the proposed bounded OFF-only recovery (maximum three sends, five-second confirmation waits). The independent STOP reference disarms, requests cancellation of the running start script, sets pending ON (even when no start was running), then sends non-retained OFF. The first three actions allow continuation on supported service errors so that OFF is not gated by successful local readback. After OFF, require arm OFF, pending ON and start script OFF; otherwise report an error and require recovery. This readback is not physical OFF proof, and a failed or hanging service or already-dispatched MQTT command can still defeat timing guarantees. Never automatically clear pending or rearm following STOP. It does not wait for natural completion of the start cycle. The existing live Telegram STOP remains unchanged, not yet routed through this reference.

## Explicit unresolved release gates

1. The firmware candidate now supplies an atomic request-bound scan, clean revision and software/GPIO OFF report. The HA reference validates its exact format and fresh-code policy offline. This is not independently verified installed-device/session evidence: prove real scan timing, request/reply delivery, stale/replayed message rejection, expected artifact/device identity, and publisher isolation. A floating sensor may appear electrically valid; ADC invalidity is not a complete disconnected-sensor detector. MQTT expiry and retained states alone remain insufficient.
2. A single MQTT state mailbox is not a guaranteed first-event queue. ESP32 #74 refuses the eight most recently admitted request IDs before any offer renewal or rescan, including failed scans; the RAM history survives STOP, expiry and reconnect in the same boot, but not reboot or eviction. It does not reject a delayed first delivery of a previously unseen ID after STOP. Under exclusive publishing and a unique request this reduces duplicate offers, but a state mailbox can still overwrite the first event before HA samples it, and a quick OFF can overwrite ON. The reference rejects changes after capture and fails closed on missed correlation, but does **not** prove strict first-offer semantics. Prove the required event capture and cancellation ordering in actual HA Core and broker/device integration before release; if necessary change the minimal protocol rather than add a general message-processing service. Random request IDs are correlation only, not durable uniqueness or authentication. A delayed ticket after STOP is not safe unless the original HA admission is irrevocably canceled. Verify STOP from every entry point, cancellation before offer, between checks and dispatch, during ON, disconnect and reconnect. Do not claim that separate HA service actions form an atomic transaction. A failed helper action, script cancellation or restart can bypass later script steps; the pending/arm defaults are proposed protection, not proven durability.
3. The 45-second device deadline currently uses cooperative firmware timing; a physical short cutoff under stalls, firmware identity, physical NO wiring, sensor calibration, and independent power isolation remain unverified. Verify day reservation and latch recovery for crash/reload/clock rollback, all direct MQTT/HA start publishers, sole scheduler, and the actual installed HA configuration. The only acceptable release is a separately reviewed source outcome with real evidence, then separate owner authorization. Do not simply remove the literal false conditions or toggle the helpers. No overlapping legacy and HA schedules; no forced watering to test a missing gate.
