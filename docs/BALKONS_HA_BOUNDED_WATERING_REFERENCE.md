The existing HA preview, Telegram STOP and legacy watering schedule are unchanged. The ESP32 candidate is merged source, not installed firmware evidence.

The native reference uses one single-mode admission script, a non-restored default-OFF owner arm latch, a default-ON incomplete-attempt latch, a reply mailbox and a disabled 11:00 local schedule. The second latch prevents an interrupted attempt from silently becoming eligible on a later day while the owner arm remains ON. No code automatically turns the arm ON. Recovery and any future arm transition require a separate reviewed procedure. The source contains literal false entry gates in both scripts and the scheduler, and additional false session/transport-proof and release conditions in the start sequence. Turning a helper or automation ON cannot release it.

## Admission and reply handling

The existing preview is a negative filter for weather, clock, date and software pump state, never a live permit. Its computed minimum temperature must be a finite numeric value strictly above 2 C, with a recognized outcome. Sensor-only preview outcomes do not establish or veto fresh sensor admission: the preview reads retained categorical entities, whereas the actual moisture gate consumes the new device scan. The date/pump/arm/pending guards remain. The current weather state, temperature and unit are captured and must remain unchanged before dispatch; this does not prove the forecast cannot change in the interim. Before any protocol dispatch latch pending. A pre-subscribed MQTT reply sensor avoids opening a one-off subscription after a fast reply.

The non-retained QoS1 request is a prefixed string `ticket45:<16 hex>`. Reject an already present matching offer prefix before dispatch. Wait at most five seconds for a matching request prefix or cancellation, capture once, then require the exact 104-character v2 payload `offer2:<16 request>:<24 ticket>:<40 revision>:<10 codes>:off`. Match the pinned firmware revision, exact lengths, lowercase hex, delimiters and OFF suffix. The old v1 format is rejected. The request and all start/ACK values remain prefixed strings to prevent native-template coercion of numeric-looking hexadecimal values. No refresh, fallback, retry, or second start. Any mailbox replacement before dispatch blocks. A malformed matching offer is not a reason to request another.

The ten codes are ordered by flowers 1, 3–10, 12. D is dry, W wet, M intermediate (blocks), U ADC-invalid/unavailable (count as assumed wet). Require <=2 U, >=2 D and W+U<8, therefore at least three D with this complete ten-channel policy. No retained moisture entity can authorize the attempt. The device scan is bounded to under two seconds and the ticket expires ten seconds from scan start; HA accepts and uses the frozen offer only within eight seconds of its request dispatch, with a five-second wait. The device still enforces the scan-start expiry. Verify date reservation/readback and unchanged weather snapshot, arm, pending, software OFF and exact frozen offer before dispatch. Any rejected or interrupted request leaves pending latched; this deliberately conservative reference requires recovery even after a no-start rejection, rather than silently permitting another attempt. The hard false conditions remain, including before ticket dispatch and before start.

A single non-retained QoS1 start uses the frozen ticket. Software ON must match it within five seconds; OFF must correlate to the same ticket and the switch must report OFF by the conservative HA deadline (45 seconds from dispatch, with the device deadline measured from earlier scan start). Missing, overwritten, late, or ambiguous replies fail closed; never repeat ON. On a clean correlated result, clear only pending; on uncertainty, keep pending latched, disarm, and use the proposed bounded OFF-only recovery (maximum three sends, five-second confirmation waits). The independent STOP reference cancels admission/disarms before sending OFF; it does not wait for the start script to finish naturally. The existing live Telegram STOP remains unchanged, not yet routed through this reference.

## Explicit unresolved release gates

1. The firmware candidate now supplies an atomic request-bound scan, clean revision and software/GPIO OFF report. The HA reference validates its exact format and fresh-code policy offline. This is not independently verified installed-device/session evidence: prove real scan timing, request/reply delivery, stale/replayed message rejection, expected artifact/device identity, and publisher isolation. A floating sensor may appear electrically valid; ADC invalidity is not a complete disconnected-sensor detector. MQTT expiry and retained states alone remain insufficient.
2. A single MQTT state mailbox is not a guaranteed first-event queue. A second offer may overwrite the first before HA samples it, and a quick OFF may overwrite ON. The reference rejects changes after capture and fails closed on missed correlation, but does **not** prove strict first-offer semantics. Prove the required event capture and cancellation ordering in actual HA Core and broker/device integration before release; if necessary change the minimal protocol rather than add a general message-processing service. Random request IDs are correlation only, not durable uniqueness or authentication. A delayed ticket after STOP is not safe unless the original HA admission is irrevocably canceled. Verify STOP from every entry point, cancellation before offer, between checks and dispatch, during ON, disconnect and reconnect. Do not claim that separate HA service actions form an atomic transaction. A failed helper action, script cancellation or restart can bypass later script steps; the pending/arm defaults are proposed protection, not proven durability.
3. The 45-second device deadline currently uses cooperative firmware timing; a physical short cutoff under stalls, firmware identity, physical NO wiring, sensor calibration, and independent power isolation remain unverified. Verify day reservation and latch recovery for crash/reload/clock rollback, all direct MQTT/HA start publishers, sole scheduler, and the actual installed HA configuration. The only acceptable release is a separately reviewed source outcome with real evidence, then separate owner authorization. Do not simply remove the literal false conditions or toggle the helpers. No overlapping legacy and HA schedules; no forced watering to test a missing gate.
