# Balcony MQTT -> Telegram notification smoke test — source-only (#1486)

## Why a test is still needed

After the separately authorized #1484 RPi5 bot source update, the
current-generation sanitized, read-only journal showed:

- `balkons-bot.service` active/running, no unexpected restarts.
- `MQTT connected=1` and matching `MQTT SUBACK accepted=1`.
- `TG API outcome source=local ok=1` (bot-local startup).
- `TG API outcome source=mqtt ok=1` **not observed**.

This is evidence of MQTT subscription and one local Telegram HTTP API
acceptance, **not** evidence that the MQTT notification path failed or
that a message has reached the intended chat. No broker or Telegram
test traffic has been authorized or generated by this issue.

## Source-only artifact: no network, credentials or side effects

Run `python3 -I -B ops/bin/balkons-bot-mqtt-notification-smoke-plan --check`
for an offline source-contract check. Run the same tool without `--check`
to emit a public, deterministic JSON **specification only**. It has no
network/API/MQTT/Telegram imports, no LIVE send mode, no secret or environment
reads and no file writes; it cannot publish a message, send a Telegram
request or control a pump. Source merge is not execution authorization.

The reviewed payload is fixed and benign:

```text
Balkona MQTT-Telegram sakaru tests. Tikai pazinojums.
```

After a *new*, exact owner-authorized LIVE decision, a separate trusted
existing HA MQTT publishing mechanism may send exactly one request with
these fixed values; the plan itself never sends:

```json
{
  "topic": "balkons/telegram_out",
  "payload": "Balkona MQTT-Telegram sakaru tests. Tikai pazinojums.",
  "qos": 0,
  "retain": false
}
```

Reviewed HA service path: `POST /api/services/mqtt/publish`.

This is a **notification-only** MQTT topic consumed by
`ops/lib/balkons-bot.py` and already used in the reviewed
`ops/bin/balcony-watering-autumn` source. It is **not**
`balkons/cmd` (the ESP32 actuator/command topic). Never use
`balkons/cmd`, `/laist`, `/stop`, an HA switch command, a wildcard topic,
QoS > 0, retain=true, or an arbitrary message in this test.

### Requirements for a later, separate LIVE decision

A future owner approval must bind the exact GitHub source SHA, host,
fixed publication route/topic, **literal payload or its exact approved hash**,
`qos=0`, `retain=false`, strictly one attempt, no retry, expected
publisher identity and target, proof window, and whether/how existing
protected HA credentials may be accessed. No previous operator, GitHub
MERGE, `--check`, or this issue authorizes HA token reads, a broker
publish or an HA API request. Do not put HA tokens into argv, GitHub
issues, process logs or command output. Never pull credentials from the
running bot's systemd credential directory into the smoke-test process.

If there is no reviewed path to delegate HA publisher credentials without
unapproved protected-data access, **BLOCKED**: do not improvise with MQTT
anonymous access, runtime token copying or a second sender.

### Evidence after an authorized single notification

1. Just before the bounded publisher action, require an independently
   authorized *strict READONLY*, sanitized service snapshot for the active
   `balkons-bot.service` invocation: active/running, successful MQTT
   CONNACK and a **matching SUBACK**, and counters for
   `TG API outcome source=mqtt ok=1/0`. Bind a non-secret generation
   fingerprint, not raw journal records or process environment.
2. Make **one** authorized HA MQTT publish to the fixed topic with
   `qos=0`, `retain=false`. No application-level retry even on
   failure, timeout or ambiguous HTTP result. HTTP 200 does **not**
   demonstrate MQTT delivery or Telegram acceptance.
3. Take a second separately scoped sanitized read-only service snapshot.
   Require **same service invocation**, no MQTT reconnect/subscription
   rejection, no queue-full event or failed Telegram HTTP send.
   A `source=mqtt ok=1` count increment supports the route but could
   reflect another message if concurrent notifications were received;
   it does **not** uniquely attribute the exact test payload.
4. The owner checks the destination Telegram chat independently for the
   *exact literal test text*. A Telegram Bot API `ok=1` only means
   API acceptance, not human receipt. The complete route is confirmed
   only with credible destination evidence; do not copy private chats
   or chat IDs to a public issue.

The test does not verify HA sensor data, weather/frost safety or the
11:00 controller. That controller replacement needs its own current
sanitized prerequisites and **separate owner LIVE authorization**;
this smoke test has no authority to change it.

## Offline CI

`tests/test-balkons-bot-mqtt-notification-smoke-plan.py` runs in the
existing `ci/validate-groups.json` balcony group, with an updated
`tests/test-validation-manifest.py` count. Tests reject changed
MQTT topics, bot subscription/provenance, HA route, retained delivery,
QoS drift, command-like payloads, symlinks and unauthorized CLI publish
arguments. All tests use repo sources or isolated temporary fixtures;
no host process, secret, MQTT broker, Telegram or pump is contacted.
