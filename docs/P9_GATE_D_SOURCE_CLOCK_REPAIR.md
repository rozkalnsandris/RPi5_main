# P9 Gate D source-App clock repair

## Status

Source-only repair for the Gate D trusted baseline source-App authentication failure observed on 2026-08-31.

This document does not authorize host/runtime mutation, GitHub App or credential changes, D1 access, baseline retry, Queue READY, genuine P9, LIVE-AUTH, workflow dispatch, deployment, rollback, cleanup, or retry.

## Observed failure

The separately authorized fresh Gate D baseline attempt reached the source-App token provider and stopped with the public-safe result:

```text
P9_GATE_D_FRESH_BASELINE_PREAUTH=PASS
P9_GATE_D_FRESH_BASELINE_AUTH_CONSUMED=YES
P9_CONTROL_BASELINE=STOP reason=P9SourceTokenStageError:source installation token provider failed stage=clock_response
P9_GATE_D_FRESH_BASELINE_WRAPPER_RC=1
```

The LIVE authorization was therefore consumed and is not reusable. No retry is permitted under that authorization.

The baseline CLI primes source authentication before entering the collector path, so this failure occurred before D1 collection or baseline evidence publication.

## Root cause

The reviewed source provider previously treated an unauthenticated GitHub REST root request as a mandatory clock dependency:

```text
GET https://api.github.com/
```

The provider required both HTTP 200 and a valid `Date` response header before it would construct the GitHub App JWT. Any request failure, non-200 response, missing Date header, or invalid Date header collapsed to the public-safe `clock_request` or `clock_response` stages.

That dependency is not required by GitHub's GitHub App JWT contract and creates an unnecessary pre-authentication failure surface. GitHub documents that JWT `iat` should be set about 60 seconds in the past to protect against clock drift and that the server's own date/time should be kept accurate, for example with NTP. The existing shared `build_app_jwt()` helper already applies the 60-second `iat` offset and a short expiry.

Canonical GitHub documentation:

- https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app

Unauthenticated REST rate limiting is one plausible reason an otherwise healthy root probe can return a non-200 response, but the sanitized runtime stage does not preserve the actual HTTP status. Therefore rate limiting is not asserted as the observed root cause; the source defect is the unnecessary unauthenticated clock dependency itself.

## Repair contract

`ops/lib/deploy_executor/p9_source_auth.py` now:

1. obtains local timezone-aware UTC with `datetime.now(timezone.utc)`;
2. builds the GitHub App JWT using the existing `build_app_jwt()` helper, which applies the reviewed `iat = now - 60` posture;
3. does **not** perform an unauthenticated GitHub root clock request;
4. performs the existing exact repository installation request:
   `GET /repos/rozkalnsandris/rozkalns-control-center/installation`;
5. requires that authenticated installation response to be HTTP 200, object-shaped, exact identity/scope, and to contain a valid GitHub `Date` header;
6. uses that authenticated GitHub server time for installation-token lifetime validation;
7. preserves the exact one-repository token request and the existing Actions read + Contents read permission boundary;
8. still mints at most one token per provider instance and reuses only that cached token.

The new public-safe failure stage `installation_clock` covers a missing or invalid `Date` header on the authenticated installation response. The obsolete pre-authentication `clock_request` and `clock_response` stages are no longer generated by the source provider.

No App ID, installation ID, owner identity, repository ID, repository-selection requirement, permission allowlist, token repository scope, or token lifetime bound is widened by this repair.
